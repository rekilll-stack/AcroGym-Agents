# API для бронирования корта в UDC — реализованные правила

Клиент `udc_booker.py` и планировщик `udc_scheduler.py` реализуют следующие правила API для бронирования корта в UDC. Проверки на реальном сервисе и проверки на подставных ответах разделены в отчёте тестирования.

## API для бронирования корта в UDC — расписание

- Часовой пояс `Asia/Qatar`, UTC+03:00.
- Запуск в 00:00 по воскресеньям, понедельникам, вторникам, средам и четвергам.
- Дата корта — местная календарная дата запуска +7 дней.
- Пятница и суббота исключены из дней запуска и целевых дней.
- Первый запуск текущего расписания: 18 октября 2026, 00:00, на 25 октября 2026.
- Должен работать один активный исполнитель на аккаунт. При переносе сначала отключается прежний.
- Отдельный планировщик хранит дату попытки, блокирует второй локальный экземпляр и не повторяет день после перезапуска. Секреты на диск не записываются.

По отдельно выраженной просьбе владельца разрешён разовый режим `--execute-once YYYY-MM-DD --window evening|morning`. Он создаёт бронь только одного явно выбранного окна на дату сегодня–+7 дней по Дохе, сохраняет ограничения будних дней, времени, кортов и длительности, проверку истории и запрет слепых повторов. Разовый режим не используется автоматическим расписанием; ограничение полуночного режима остаётся прежним. Оплата вручную.

## API для бронирования корта в UDC — окна и длительность

| День корта | Окно | Приоритет |
| --- | --- | --- |
| Воскресенье | 18:00–21:00 | 18–20 или 19–21, два часа подряд |
| Понедельник | 18:00–21:00 | Два часа подряд |
| Понедельник дополнительно | 07:00–09:00 | 07–09, независимо от вечерней брони |
| Вторник | 18:00–21:00 | Два часа подряд |
| Среда | 18:00–21:00 | Два часа подряд |
| Четверг | 18:00–21:00 | Два часа подряд |
| Пятница, суббота | Нет | Бронирование исключено |

Пара должна быть на одном корте. Сначала проверяются оба допустимых корта на наличие пары. Только если пары нигде нет, выбирается один час как запасной вариант. Полный час должен находиться внутри окна. Максимум два часовых резерва на одно окно; в понедельник допустимо до двух часов утром и до двух вечером. API обоих кортов при проверке вернул `[60]`, поэтому пара оформляется двумя отдельными запросами на соседние часы. Разрешение сервера на фактическое создание второй брони предстоит проверить в первом реальном запуске.

## API для бронирования корта в UDC — объекты

- Giardino / GV: `b69ef8b8-fe79-ec11-8d22-0022489cbcfa`.
- Family Park / Costa Malaz: `b89ef8b8-fe79-ec11-8d22-0022489cbcfa`.
- Подходит любой из двух. При отсутствии времени на одном выбирается подходящий другой.
- Только теннис: текущий `amenityTypeId = 100000001` проверяется по каталогу Giardino/GV. Другой вид спорта в слотах Family Park исключается.
- При отсутствии подходящих слотов бронь за пределами окна или на другом объекте не создаётся.

## API для бронирования корта в UDC — история и частичный результат

Перед созданием и после каждого успешного ответа проверяется собственная история: дата, объект, часы, цена, статус, срок истечения. Неистёкшие резервы, ожидающие оплаты, также учитываются.

- Два уже имеющихся часа блокируют дополнительные брони в том же окне. Если они не идут подряд, результат помечается для проверки владельцем.
- Один имеющийся час дополняется только соседним часом на том же корте. Отдельная пара поверх него не создаётся.
- При отказе второго часа первый сохраняется. Самостоятельной отмены нет.
- Явный конфликт доступности позволяет перечитать слоты и выбрать подходящий вариант; максимум три запроса создания на окно.
- Таймаут, HTTP 5xx, непонятный ответ, неподтверждённый идентификатор или отсутствие созданной записи в истории приводят к остановке дальнейшего создания. История перечитывается, слепого повтора нет.
- Изменение цены созданного часа, расхождение объекта/времени и непроверяемое состояние останавливают дальнейшие действия.
- Требования QID, договора аренды, документов или иных дополнительных действий передаются владельцу аккаунта. Условия сервера, тарифы и лимиты не обходятся.

## API для бронирования корта в UDC — оплата

- Платит владелец самостоятельно по официальной ссылке, полученной через API для бронирования корта в UDC.
- `Payment/paymentAuth` вызывается для идентификатора своей конкретной ожидающей оплаты брони. Тело содержит её фактическую сумму, `QAR` и `bookedAmenityId`.
- Для двух отдельных часовых броней выводятся отдельные ссылки и суммы. Общая сумма не подставляется под один идентификатор.
- Тариф берётся из ответа сервера; произвольных скидок нет. Нулевой тариф не требует создания платёжной сессии.
- Уже оплаченные записи пропускаются. При неизвестном статусе/сумме выводится необходимость проверки.
- Данные карты не запрашиваются и не передаются. Автоматическое списание, отправка документов и дополнительных персональных данных не реализованы.
- Срок оплаты и срок истечения берутся из реальных ответов. Фиксированный срок не выдумывается.
- Подтверждение — `status = Active` и `paymentStatus = Confirmed` по каждому часу. Получение ссылки и ожидание оплаты не считаются окончательным подтверждением.
- `--status` проверяет состояние после оплаты. `--payment-links` создаёт только ссылки для существующих собственных резервов.

## API для бронирования корта в UDC — результат

По каждому нужному окну выводятся дата, корт, часы, фактическая длительность, цена каждого часа, общая сумма, идентификаторы и номера броней, статусы, платёжные ссылки, сроки и причина частичного результата либо отсутствия мест. Непроверенная новая запись помечается `Unverified`. Пароли, токены и лишние сведения профиля не выводятся. Данные входа предоставляются отдельно через скрытый ввод или настройки секретов исполнителя.

## API для бронирования корта в UDC — точность времени

Цель автоматического расписания — запуск в 00:00 Дохи. Режим `--execute-scheduled` разрешает записи только 00:00–00:05 и проверяет время перед каждым созданием. Отдельно разрешённый владельцем разовый режим проверяет выбранную дату и окно перед каждой записью. Подготовка окружения, вход и сеть могут задержать первый запрос относительно 00:00:00. Точное время поступления запроса на сервер не гарантируется. Постоянный отдельный хост и уже готовое окружение уменьшают задержку; создание резерва всё равно зависит от доступности UDC.

Транспорт: ожидание до 60 секунд на попытку. Только вход и чтение каталога, слотов и истории повторяются при транспортной ошибке, HTTP 408 или HTTP 5xx, максимум три попытки всего с паузами 2 и 4 секунды. Создание брони и платёжной сессии не повторяются после неопределённого ответа. В ошибке чтения выводятся только маршрут, этап, тип ошибки и счётчики, без секретов и содержимого запросов.

## API для бронирования корта в UDC — проверено и осталось проверить

Реализованы выбор двух часов, дополнение одного часа, запасной один час, расписание, понедельник с двумя окнами, защита от дублей и неопределённых записей, платёжные ссылки и вывод статусов. Автоматические тесты пройдены. Вход, каталог, история, слоты и длительности проверены на реальном API.

16 октября 2026 отдельно разрешённая владельцем реальная бронь AB-49363 успешно создана: Giardino 19 октября 08:00–09:00, Active / Confirmed, 0 QAR. Передача подтверждения принята сервером с calendar=true. Реальная пара на два часа, получение платёжной ссылки для платного резерва и подтверждение нового платежа пока отдельно не проверены.

Если bookingDate и bookingTimeSlot заданы, время проверяется по локальному слоту Дохи. Допускается совпадение со служебными UTC-метками либо обнаруженный на реальной записи одинаковый трёхчасовой сдвиг обеих меток. Другие расхождения останавливают обработку. При отсутствии отображаемого слота используется обычное преобразование UTC. Правило Active / Confirmed и ожидание подтверждения обоих резервов сохраняются.

Двенадцатичасовой срок оплаты не обещается. В прочитанной истории 54 платных резервов bookingExpiry было через пять минут после createdDate. При новой платной брони сообщаются фактические сроки из UDC; срок самой платёжной сессии не считается проверенным по сроку резерва.

## API для бронирования корта в UDC — передача подтверждённых броней

После подтверждения каждого часа (`Active / Confirmed`) передать на `POST https://hook.acrogym.org/tennis` только `date`, `from`, `to`, `court`. Часы по Дохе. Соседние часы того же корта объединяются. Если один из двух резервов ещё ожидает оплаты, отправка этого окна ждёт подтверждения обоих. Один подтверждённый час как окончательный запасной вариант передаётся отдельно. Имена, телефоны, QID, стоимость, платёжные ссылки и документы в этот запрос не включаются.

При `calendar: true` сообщать о добавлении в календарь и Джарвис. При `calendar: false` сообщать, что сервер принял запись и календарь будет добавлен позже. При `duplicate: true` считать запись уже существующей, повтор не нужен. При 400 исправлять только подтверждённые данные/формат по ошибке; неизвестные поля и факты не выдумывать. При 401 прекратить попытки с этим ключом; при 403 прекратить отправку до исправления доступа владельцем сервера. При сетевой ошибке или HTTP 5xx разрешены максимум три повтора после первоначального запроса с паузой 60 секунд и тем же телом. После исчерпания попыток сообщить владельцу; бесконечных повторов нет. Непроверяемый ответ HTTP 200, 401 и 403 автоматически не повторяются.

Сервер, согласно предоставленному контракту, сам добавляет игру в календарь, раздел тенниса и уведомляет владельца. Клиент напрямую эти действия не выполняет. Подавление повторной заявки другим агентом относится к серверной стороне и не проверено этим клиентом.

Для своевременного обнаружения оплаты написан отдельный `udc_confirmation_worker.py` с проверкой раз в 60 секунд на постоянно включённом хосте. Он не создаёт новые резервы или платёжные сессии и останавливается при ошибке. Это отдельный процесс проверки подтверждений; один исполнитель создания броней остаётся обязательным. Доступ к новому адресу проверен безопасным запросом. Для этой среды используется отдельное задание проверки подтверждений; самостоятельный процесс из архива предназначен для постоянно включённого внешнего хоста.
